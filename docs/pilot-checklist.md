# Lecturer pilot checklist

Use one unit alongside or shortly after the corresponding topic is taught. Start with a small group, for example three to five students. The aim is to learn whether the material fits your teaching; the units have not yet been trialled externally.

<a class="vm-button" href="handouts/lecturer-pilot-checklist.pdf">Download the printable checklist (PDF)</a>

Use the [lecturer guide](supervisors.md), [Getting started](getting-started.md),
[A1](units/ode-ivp/index.md) or [A2](units/linear-systems/index.md)
for the detailed instructions. GitHub is optional; the usual route is a ZIP download.

## Before assigning

- Choose A1 (ODE initial-value methods) or A2 (iterative linear solvers). A1 is not required before A2.
- Check the mathematical prerequisites and basic Python/NumPy skills. Try setup on a computer like those students will use.
- Look at an example report and the marking rubric. Run the starter files: an incomplete report is expected.
- Agree the tutorial sections, experiments, written explanation, deadline and course rules for help and AI use. Record the unit version and keep the downloaded ZIP.

## During the practical

- Ask students to save changes in student/steps.py and rerun python verify.py. Keep the supplied checker unchanged.
- Record setup problems, time spent helping and unclear instructions. Ask students to explain what one check or plot means.
- For offline study, save the formatted web sections as PDFs while connected. Code, bundled data and generated reports run offline after installation.

## When assessing

- For a full unit, request python verify.py --strict, the student folder, generated report and agreed write-up. For a one-method exercise, assess that method's results; whole-unit strict mode will reject unfinished methods.
- Inspect the submitted code, rerun it in a fresh copy of the same unit version, and compare code and checker fingerprints.
- Use the rubric and a few viva questions to assess understanding. Passing the supplied checks is evidence about those cases, not proof of authorship or the validity of an entire project.

## Feedback after the trial

- Tell us the unit/version, course level, number of students, operating systems and Python versions used.
- What prevented progress? How much support and assessment time was needed? What could students explain afterwards?
- Would you assign it again, and what one change would matter most? Email feedback without student identifiers; discuss any student work you would like to share first.
